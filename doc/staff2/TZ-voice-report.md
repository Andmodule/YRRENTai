# ТЗ: голосовой отчёт персонала (Staff) — 2026

Документ фиксирует продуктовые требования и техническую архитектуру по согласованию с командой. Реализация идёт поэтапно; статус этапов см. в конце.

## 1. Цели

- Дать уборщице/водителю **быстрый отчёт по задаче** без длинных форм: голос → структура → одно подтверждение.
- **Zero-Error Tolerance**: выбор режима кнопкой — это *prior*, не жёсткий фильтр; LLM определяет фактический режим и смешанные сценарии.
- **Атомарность**: один API-вызов на сабмит (обновление задачи + создание инцидента при необходимости) — всё или ничего; идемпотентность по `clientRequestId` (позже).

## 2. Персоны и контекст

- Пользователь занят, речь может быть короткой и несистемной; **строгий порядок слов не требуется** — парсинг на стороне LLM.
- Доступ: **frontend-staff** (Mini App / браузер), роль `STAFF`, текущая задача из списка (контекст `taskUuid`, `propertyId`).

## 3. UX: главный экран (матрёшка)

### 3.1 Оранжевая кнопка (текстовый/ручной инцидент)

- Существующий сценарий **не удалять**: FAB открывает ручной ввод инцидента (`IncidentReportDrawer`).
- **Позиция**: закрепить **слева** внизу (`fixed`, safe area), чтобы справа осталось место под голосовой вход.

### 3.2 Две кнопки режима (prior)

| Кнопка | Визуальный вес | Назначение |
|--------|----------------|------------|
| **Задача** | Крупнее (главная) | Отчёт по статусу уборки / выполнению. |
| **Инцидент** | Меньше | Акцент на событии/проблеме. |

Обе открывают **один и тот же** bottom sheet голосового отчёта с предустановленным `buttonPressed: 'TASK' | 'INCIDENT'`.

### 3.3 Один микрофон внутри sheet (как у менеджера)

- **Одна** кнопка управления записью внизу шита:
  - до записи — «Начать запись»;
  - во время записи — **«Завершить запись»** (явное окончание, как в `SmartCreateSheet` / `stopRecording`).
- Автоостановка по тишине/макс. длительности — **как в менеджерском** `useVoiceRecorder` (подстраховка); основной сценарий — пользователь сам нажимает «Завершить».

### 3.4 Контекстные микро-подсказки (2–3 строки)

Меняются от выбранного режима (prior):

- **Задача**: «Что сделали → статус (готово / в процессе) → чего не хватает. О поломках можно сказать в том же сообщении.»
- **Инцидент**: «Что случилось → где → насколько срочно. Достаточно одной фразы.»

### 3.5 Вилка после распознавания

1. **Всё однозначно** → экран ревью с заполненной формой (редактирование полей по желанию).
2. **Нужны уточнения** → краткие вопросы текстом → повторная обработка (второй голосовой ввод или одна строка текста) → снова ревью.

### 3.6 Экран подтверждения (Confirmation)

- **Одна основная кнопка**: «Отправить».
- Отказ: **крестик** в шапке и/или **свайп вниз** (закрыть без отправки).
- При смешанной речи (пример: режим «Задача», в речи — зеркало): **две карточки** — ✅ задача (статус) и ⚠️ инцидент (риск, при высоком риске — акцент + предложение фото).
- Мягкая приписка при несовпадении prior и содержания (симметрично для обоих режимов).

## 4. Бэкенд (NestJS + LLM) — контракт

### 4.1 Вход

- `multipart`: аудио + метаданные:
  - `buttonPressed`: `'TASK' | 'INCIDENT'`
  - `taskUuid`: UUID текущей задачи
  - опционально `clientRequestId` (UUID) для идемпотентности

### 4.2 Выход (схема, например Zod)

- `buttonPressed` (echo)
- `detectedMode`: `'TASK_ONLY' | 'INCIDENT_ONLY' | 'MIXED'`
- `confidence`: по полям или агрегат
- Структурированные поля: статус задачи, комментарий, блок инцидента (тип, описание, риск), уточняющие вопросы при `needsClarification`

### 4.3 Сабмит

- **Один** endpoint: атомарная транзакция — PATCH задачи + создание инцидента при необходимости.
- После успешного коммита: **Socket / push менеджеру** о новом инциденте (настраиваемая политика по шуму).

## 5. Связь с кодовой базой

- Менеджер: `frontend-user` — `SmartCreateSheet`, `useVoiceRecorder`, `parseVoiceTaskAudio` (`/tasks/voice-parse`).
- Staff: `frontend-staff` — отдельное приложение; переиспользуем **паттерн** записи и нижней кнопки «Завершить», отдельный endpoint отчёта по задаче (после реализации на бэкенде).
