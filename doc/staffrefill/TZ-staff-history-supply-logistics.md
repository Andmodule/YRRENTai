# ТЗ: доп. комментарии в «Истории», LLM-классификация, снабжение и логистика (Staff / Manager / Logistics)

**Версия:** 1.2  
**Статус:** черновик ТЗ для согласования  
**Связанные экраны:** Staff — «История», **создание новой задачи** (и иные точки ввода текста); Manager — дашборд; будущие роли — логист / водитель.

---

## 1. Цели и проблема

### 1.1 Текущее состояние

- В приложении персонала есть экран **«История»**: завершённые задачи и созданные сотрудником инциденты, с возможностью **дополнить фото** постфактум.
- Отдельного явного раздела **«чего не хватает»** / **«что нужно сделать»** (снабжение, логистика, стирка, вывоз белья и т.д.) **нет** — это создаёт пробел между фактом уборки и операционными действиями склада/водителя/прачечной.

### 1.2 Цели продукта

1. При **нажатии на карточку** (не только на кнопку «Добавить фото») дать сотруднику возможность ввести **дополнительный текстовый комментарий** к уже существующей карточке (задача или инцидент в истории).
2. Применять **тот же алгоритм классификации и извлечения намерений (LLM)** не только к дополнениям в «Истории», но и к **свободному тексту при создании новой задачи** (описание, заметки, комментарий при создании — конкретное поле задаётся в API/UI), чтобы фразы вроде «нет белья», «нужна бумага» фиксировались системой **уже на этапе создания**, а не только при последующем редактировании/дополнении.
3. Обрабатывать указанный текст **через единый конвейер LLM** (см. §3.0), чтобы:
   - отличать **инцидент** (поломка, ущерб, нарушение) от **запроса на пополнение / снабжение** («нет белья», «закончилась бумага»);
   - выделять структурированно **дефициты** и **намерения** для последующего согласования менеджером.
4. **Фиксировать точное время** каждого ввода/события (и хранить автора, привязку к сущности или к факту создания).
5. Заложить концепцию **2026**: автоматическая логистика где возможно, **верификация менеджером** перед выдачей работы водителю/курьеру по материальным ценностям, отдельный слой **Supply / Logistics** в UI менеджера и в будущем — у логиста.

## 2. Пользовательские сценарии (Staff)

### 2.1 Карточка в «Истории»

| Действие | Ожидание |
|----------|----------|
| Нажатие на **область карточки** (основной контент) | Открывается **нижнее меню / sheet** с заголовком контекста (объект, тип задачи/инцидента, краткая метка времени). |
| В sheet | Поле **многострочного ввода** «Дополнение к отчёту» (или аналог), кнопка **«Дополнить»** (отправить). |
| Опционально в том же sheet или вторым шагом | Кнопки быстрых действий: **«Добавить фото»** (существующий поток), **«Отмена»**, закрытие по свайпу. |
| После успешной отправки | **MVP:** см. §4 (toast + optimistic UI; отдельный экран ревью — V2). |

### 2.1а Создание новой задачи (тот же LLM-конвейер)

| Действие | Ожидание |
|----------|----------|
| Пользователь создаёт задачу и вводит **текст** в согласованное поле (описание / комментарий / заметка при создании) | После сохранения задачи тот же **pipeline §3.0** обрабатывает текст: инцидент vs снабжение vs прочее. |
| Результат для менеджера | Как и для дополнений: черновики supply / инцидент **без прямой выдачи водителю** без верификации (§6). |
| Время | Фиксируется время создания записи и/или отдельная метка времени обработки LLM — согласовать с моделью данных (§5). |

*Примечание:* реализация не должна дублировать две разные схемы JSON для «история» и «создание»; допускается различие только в **контексте промпта** (`entry_point: history_supplement | task_create | …`).

### 2.2 Ограничения и валидация

- Минимальная длина текста (например 3–10 символов), максимум (например 2000–8000 символов) — согласовать с бэкендом.
- Rate limiting на пользователя / карточку — защита от спама.
- Повторные дополнения **разрешены** (несколько записей во времени); каждая запись — своё **точное время** (см. §5).

### 2.3 Доступ

- Только **свои** задачи (исполнитель) и **свои** инциденты (репортёр), в рамках уже реализованных правил API.

## 3. Поведение LLM (оркестрация)

### 3.0 Единый модуль интерпретации текста (обязательное требование)

- Один **контракт входа/выхода** (схема JSON §3.2) и одна **логика пост-обработки** (политика «не к водителю без менеджера», запись `llm_payload`, состояния workflow) для всех **точек входа**:
  - дополнение к карточке в **«Истории»**;
  - **создание новой задачи** с текстом в согласованном поле;
  - (расширение) заметки к задаче, голосовой отчёт с транскриптом — **тот же pipeline**, иной только `entry_point` и контекст в промпте.
- **Запрещено** вводить отдельную «упрощённую» классификацию только для одного экрана без явного исключения в ТЗ на ревью.

### 3.1 Вход

- Текст пользователя (дополнение **или** текст при создании задачи **или** иной согласованный источник).
- Контекст (передаётся в промпт, не обязательно показывать целиком пользователю): **`entry_point`**, тип сущности (задача / инцидент / черновик задачи), `propertyId`, при необходимости — тип задачи, краткое описание инцидента, язык интерфейса.

### 3.2 Выход (структурированный JSON)

Минимальная схема (имена полей — для согласования с разработкой):

- **`intent`**: одно из (примерный перечень):
  - `INCIDENT_FOLLOWUP` — похоже на новый или уточняющий инцидент (поломка, ущерб, эмердженси).
  - `RESTOCK_REQUEST` / `SUPPLY_SHORTAGE` — «чего не хватает», расходники, бельё, мелкий ремонт без инцидента как ущерб.
  - `LOGISTICS_HANDOFF` — явный запрос на забор/доставку (бельё, мусор, ключи) **как намерение**, если продукт вводит сущность «логистическая задача».
  - `NEEDS_CLARIFICATION` — недостаточно данных; система может задать 1–2 уточняющих вопроса в UI (опционально, фаза 2).
  - `NO_ACTION` / `NOTE_ONLY` — нейтральная заметка без последствий для снабжения/инцидентов.

- **`confidence`**: число 0–1 (для правил авто-маршрутизации и UI «светофора» у менеджера).

- **`extracted`** (примеры полей):
  - `items`: массив `{ name, quantity?, unit? }` — «бумага 2 рулона», «полотенца».
  - `location_hint`: строка или ссылка на объект (если из текста).
  - `severity`: для инцидентов — `low|medium|high` (если применимо).
  - `suggested_incident_type`: если инцидент — маппинг на существующие типы в системе.

- **`staff_facing_summary`**: одна строка для **V2**-экрана подтверждения («Мы поняли так: …»); в **MVP** может использоваться только в логах/админке или не показываться пользователю (см. §4).

### 3.3 Правила безопасности и бюджета

- **Никакого прямого** создания задач водителю/курьеру по материальным ценностям **без слоя верификации** (менеджер или настроенный авто-аппрув по политике — см. §6).
- LLM **не** является источником истины для складских остатков; только классификация и извлечение намерений.

### 3.4 Провайдер

- Использовать согласованный в проекте стек (например DeepSeek для JSON + при необходимости отдельный проход для строгой схемы). Ошибки парсинга JSON → fallback: сохранить «сырой» комментарий + флаг `parse_error` для ручной обработки менеджером.

## 4. UI после отправки текста у горничной — жёсткий скоуп MVP vs V2

**Проблема предыдущей редакции:** два равноценных варианта без выбора не дают разработчикам основания для вёрстки MVP.

### 4.1 MVP (обязательно)

- **Вариант A — единственный для первой поставки:**
  - **Optimistic UI** где применимо: комментарий / созданная задача с текстом отображаются в интерфейсе без ожидания завершения LLM; при ошибке сети — откат или сообщение об ошибке по правилам продукта.
  - **Toast** (короткое подтверждение): например «Сохранено» / «Учтём» / «Передано менеджеру на разбор» — формулировки согласовать; **без** обязательного второго шага «подтвердите интерпретацию».
  - Тексты toast **не** обещают автоматическую доставку водителю без аппрува менеджера.
- Отдельный **полноэкранный / многошаговый экран ревью** с карточками «как поняла система» в **MVP не входит**.

### 4.2 V2 (явно не MVP)

- **Вариант B:** отдельный экран или sheet **подтверждения** с 1–3 карточками:
  - «Инцидент: …» (если `INCIDENT_FOLLOWUP`) — кнопки «Отправить менеджеру» / «Исправить текст».
  - «Запрос на снабжение: …» (если `RESTOCK_REQUEST`) — **не** «уехало водителю», а «передано менеджеру на согласование».
  - При необходимости третья карточка: нейтральная заметка.
- Использование поля **`staff_facing_summary`** (§3.2) как основного текста на этих карточках.

### 4.3 Поведение UI на 1–5 секунд ожидания LLM (критично)

- **Клиент не блокируется** ожиданием ответа DeepSeek: типичная задержка 1–5 с не должна показываться полноэкранным спиннером, блокирующим весь интерфейс.
- **Целевой поток (MVP):**
  1. Пользователь нажимает «Отправить» / «Дополнить».
  2. API **сразу** принимает запрос, **сохраняет** событие с точным `created_at` и возвращает **201/200** с идентификатором события и `llmStatus: pending` (или эквивалент).
  3. **Optimistic UI:** локально показывается успех (галочка / строка в списке / закрытие sheet — по правилам экрана) и **toast** «Сохранено» / «Учтём»; пользователь может **закрыть приложение** или перейти дальше — данные уже приняты сервером.
  4. **Парсинг LLM выполняется на бэкенде асинхронно** (после ответа HTTP): очередь / `setImmediate` / worker — без удержания соединения с клиентом.
  5. При ошибке LLM текст **уже сохранён**; статус события `failed` / `llm_payload` с флагом ошибки; клиент **не обязан** ждать — менеджер обрабатывает вручную при необходимости.
- Синхронное ожидание DeepSeek в HTTP-запросе staff **не допускается** в целевой архитектуре (допустим только как временный dev-режим с флагом).

## 5. Данные и время

### 5.1 Что хранить на каждое событие (дополнение / привязка к созданию задачи)

| Поле | Назначение |
|------|------------|
| `id` | UUID записи |
| `author_id` | Staff |
| `entry_point` | `history_supplement` \| `task_create` \| … (расширяемо) |
| `target_type` | `task` \| `incident` \| иное согласованное |
| `target_id` | UUID задачи или инцидента (после создания задачи — её UUID) |
| `text_raw` | Исходный текст |
| `created_at` | **Точное время сервера** фиксации ввода/события (UTC + отображение в локали клиента) |
| `llm_payload` | JSON ответа LLM (или null при ошибке) |
| `workflow_state` | например `pending_manager` \| `merged_to_incident` \| `supply_draft` \| `no_action` |

*Для создания задачи:* либо одна запись с привязкой к созданной задаче после commit, либо отдельная таблица событий с тем же контрактом — **схема БД фиксируется на этапе проектирования API**, принцип «один pipeline» сохраняется.

### 5.1а Реляционное хранение извлечённых позиций (для «светофора» и дашборда)

- Колонка **`llm_payload` (JSON)** обязательна как **сырой снимок** ответа LLM (отладка, воспроизводимость, версионирование промпта).
- **Недостаточно** одного JSON для агрегирования «сколько рулонов на объект», фильтров и **светофора** по строкам (§6): в БД вводятся **нормализованные строки**.
- Минимальная модель (имена уточняются в миграциях):
  - сущность **шапки события** (например `StaffInterpretationEvent` / `SupplyRequest` — одна запись на одно отправленное дополнение);
  - сущность **`SupplyRequestItem`** (или эквивалент): отдельные строки с полями вроде `name`, `quantity`, `unit`, опционально `trafficLight` / `anomaly` для менеджера, **FK на событие интерпретации**.
- Заполнение: после успешного парсинга LLM worker **транзакционно** пишет JSON + **UPSERT/удаление+вставка** строк позиций из `extracted.items`.
- Индексы: по `propertyId`, `companyId`, `createdAt`, статусу верификации — для списков менеджера.

### 5.2 Аудит

- Неизменяемость `created_at`; правки текста после отправки **запрещены** или только через отдельную «правку» с новой записью (политика продукта).

## 6. Менеджер: Supply Dashboard и верификация

### 6.1 Принцип «Smart Workflow Approval»

1. **Инициация (Staff)** — голос, **текст дополнения в «Истории»** или **текст при создании задачи** (и т.д.) → через единый LLM-pipeline → структурированный **Supply Request** / черновик инцидента.
2. **Система** — фоновые проверки (если есть склад/лимиты): флаги «в норме» / «аномалия» (не блокируют сохранение запроса).
3. **Менеджер** — вкладка **«Снабжение и логистика»** (рядом с канбаном задач): сводная таблица на день/неделю, группировка по объектам, **светофор** по строкам.
4. **Диспетчеризация** — только после **«Утвердить»** (по строке или пакетно) формируются задачи для логистики/водителя (picking list / маршрут).

### 6.2 Исключения

- **Auto-approval** для дешёвых SKU по политике компании (настраивается, не обязательно в MVP).

## 7. Логист / водитель (концепция 2026, не MVP обязательно)

- UI **маршрутными точками** (waypoints), не чек-листом комнат.
- На точке: «Забрать», «Доставить», «Инцидент → мастер» — агрегировано из утверждённых менеджером заданий.
- Кнопка «Выполнено на объекте» закрывает пул утверждённых логистических операций по адресу (политика закрытия — отдельное ТЗ).

## 8. Zero-Touch Logistics (автогенерация)

**Идея:** при событии «уборка после выезда завершена» бэкенд **может** автоматически создавать черновик **Logistics Task** (например «забрать грязное бельё») **без ручного ввода** горничной.

### 8.1 Условия

- Правила привязаны к типу задачи, объекту, договорённостям с владельцем (feature flags).
- Автозадача попадает не к водителю сразу, а в **очередь согласования** или в авто-аппрув по политике (см. §6).

### 8.2 Связь с доп. комментариями

- Ручной доп. комментарий не заменяет Zero-Touch, а **дополняет** (например уточнение «белья меньше обычного»).

## 9. Нефункциональные требования

- Локализация строк UI (RU/EN минимум).
- Доступность: крупные зоны нажатия, читаемость карточки + sheet.
- Производительность: HTTP-ответ персоналу **без ожидания** завершения LLM (см. §4.3); при сбое LLM — сохранить текст и асинхронно завершить/повторить обработку; уведомление менеджера — по политике продукта.

## 10. Критерии приёмки (MVP текстового дополнения)

1. Нажатие на карточку в «Истории» открывает sheet с вводом и кнопкой «Дополнить».
2. **Создание новой задачи** с текстом в согласованном поле проходит через **тот же** LLM-pipeline, что и дополнение в «Истории» (один контракт §3.2, различается `entry_point` и контекст).
3. Сервер сохраняет запись с **точным `created_at`** и привязкой к задаче/инциденту (или к событию создания задачи по схеме §5.1).
4. LLM возвращает структурированный результат; при ошибке — деградация с сохранением сырого текста.
5. Материальные запросы **не** создают задачу водителю без статуса верификации менеджером (или явной политики авто-аппрува).
6. **UI после отправки — только MVP §4.1** (optimistic + toast); экран ревью с карточками **не** входит в критерии приёмки MVP.
7. В интерфейсе менеджера предусмотрено место/поток для списка таких запросов (хотя бы список «черновиков снабжения»), даже если полный Supply Dashboard — фаза 2.

## 11. Вне скоупа данного документа (явно)

- Полная интеграция склада (WMS), пар-уровней по квартирам без проектных данных.
- Мобильное приложение водителя как отдельный релиз.
- **Экран подтверждения интерпретации LLM (Вариант B, §4.2)** — отдельный релиз (V2), не MVP.
- Голосовой ввод в этом ТЗ — перекрёстная ссылка на существующий голосовой отчёт; детали — в отдельном ТЗ; при включении в продукт — **тот же pipeline §3.0**.
