# ТЗ: Smart Dispatching — маршруты водителя (Route / Stop), пул доставки

**Версия:** 0.1  
**Статус:** проектирование / согласование  
**Связь:** `TZ-staff-history-supply-logistics.md` §6; текущий код: `supply_request_items`, матрица снабжения, `lineStatus`, передача водителю.

---

## 1. Цель

Перейти от модели «менеджер подтверждает каждую строку → строка уезжает водителю» к модели **2026**:

- Менеджер утверждает **пакет позиций** и отправляет их в **единый пул доставки на смену/день**.
- Система строит **маршрут** (Route): склад → остановки по объектам (`propertyId`), с разбивкой **что везти куда**.
- На маршрут целиком назначается **водитель** (не на каждую бутылку отдельно).
- Водитель работает в **линейном UX**: склад (picking) → остановка 1 → остановка 2… без канбана задач.

**Гибкость для водителя (обязательное требование):** водитель может **сам выстроить порядок остановок** (перестановка waypoints), если это допускает политика компании; навигатор «следующая точка» подстраивается под выбранный или системный порядок. Системный автопорядок (по расстоянию / времени) — опция; ручной override — первый класс.

---

## 2. Термины

| Термин | Описание |
|--------|----------|
| **Пул доставки (Delivery pool)** | Набор утверждённых строк `supply_request_items` (и/или будущих логистических строк), попавших в «отправку на сегодня» до формирования маршрута. |
| **Маршрут (Route / DeliveryRun)** | Один «рейс»: дата/смена, склад отгрузки, список остановок, статус (черновик / назначен / в работе / завершён). |
| **Остановка (Stop / Waypoint)** | Точка маршрута: тип `warehouse_pickup` \| `property_dropoff` \| опционально `property_pickup` (обратная логистика). Привязка к `propertyId` для drop-off/pick-up на объекте. |
| **Маршрутный лист (Run sheet)** | Снимок состава маршрута для печати/UI: что забрать на складе, что отдать на каждой остановке. |
| **Назначение** | Связь `Route` ↔ пользователь с ролью водитель (или внешний исполнитель), одна на весь маршрут. |

## 3. Привязка к текущей архитектуре RentAI

Уже есть:

- `staff_interpretation_events` → `supply_request_items` (строки дефицита, количества, `supplyItemId`, `lineStatus`: `pending` → `handed_to_driver` → `delivered` и т.д.).
- Менеджерская **матрица** агрегирует строки по номенклатуре и **объекту** (`propertyId`) — это естественный вход для группировки **по адресам** при формировании остановок.
- Операция «передать водителю» сегодня меняет статус строк; в целевой модели она либо заменяется на **«включить в пул / в маршрут»**, либо остаётся как этап до появления сущности `Route`.

Целевое развитие:

1. Новые сущности БД (рабочие имена):  
   `delivery_routes` (или `logistics_routes`), `delivery_route_stops`, связь **многие-ко-многим** между остановками и строками поставки (`supply_request_items` через junction `delivery_stop_lines` с количеством к выдаче на этой остановке).
2. **Склад** как первая остановка: либо `propertyId` null + `kind = warehouse`, либо отдельная сущность склада компании (v2).
3. Водительское приложение (отдельный клиент или роль STAFF/DRIVER в существующем) читает **назначенный маршрут** и отдаёт события: `picking_completed`, `arrived_at_stop`, `dropoff_completed`, фото.

## 4. Флоу менеджера (Smart Dispatching)

### Шаг 1 — Утверждение (как сейчас, расширение кнопки)

- В сводной таблице снабжения менеджер отмечает позиции (по SKU и/или сырым строкам) и нажимает **«Отправить в доставку»** (рабочее имя; может заменить текущий «Передать водителю» на уровне продукта).
- Результат шага: выбранные строки попадают в **пул на дату/смену** (`poolId` или фильтр по `scheduledFor = today` + статус строки `approved_for_dispatch` — уточняется в миграции).

### Шаг 2 — Формирование маршрутного листа (Run sheet)

- Система берёт все строки пула и **группирует по `propertyId`** (и по складу для pick-up).
- Автоматически создаётся черновик **Route**:
  - **Stop 0:** склад — агрегированный picking list (сумма по SKU: 15 рулонов, 3 ершика…).
  - **Stop 1..N:** объекты с разбивкой «что оставить» на каждом адресе.
- Порядок остановок **по умолчанию**: эвристика (расстояние, фиксированный приоритет зон, время окна) — конфигурируемо позже.

### Шаг 3 — Назначение водителя

- Менеджер видит карточку маршрута («Утренний развоз — Центр») и назначает **одного водителя** на весь Route (drag-and-drop на исполнителя или выбор из списка).
- Опционально: **auto-assign** по сменам/графику (отдельная подсистема, флаг компании).

### Гибкость менеджера

- Объединение нескольких пулов в один маршрут, разбиение маршрута на два — v2.
- Редактирование порядка остановок до выдачи водителю — v1 желательно.

## 5. Флоу водителя (Driver UX — линейный)

### Экран A — Смена и склад (Picking)

- Одна первичная CTA: **«Начать смену»** (переводит маршрут / смену в статус `in_progress`, фиксирует время).
- Список **Picking list** — только агрегаты по SKU с иконками/единицами.
- Кнопка **«Погрузка завершена»** → разрешает переход к первой дорожной остановке (или к навигации).

### Экран B — Таймлайн остановок (Stops)

- Вертикальный список: **Остановка 1: [адрес]**, **Остановка 2: …**  
- Водитель может **изменить порядок** остановок (если политика `driver_can_reorder_stops = true`), с пересчётом «следующей точки» в навигаторе (deep link во внешние карты — опционально).

### Экран C — Точка (Drop-off / встречный pick-up)

- **«Я на месте»** → показать только позиции для **этой** остановки (и встречный «забрать бельё», если в маршруте есть обратная логистика, отдельная строка/флаг).
- Чекбоксы / фото подтверждения.
- **«Завершить остановку»** → следующая точка в таймлайне; при последней — «Завершить маршрут».

### Критерии UX (2026)

- **Zero confusion:** один активный шаг; нет канбана задач на весь день.
- **Batching:** один маршрут = одна погрузка, много адресов.
- **Double verification:** сверка на складе (сумма) + сверка на адресе (поштучно по остановке).

## 6. Модель данных (черновик для миграций)

Минимальный набор таблиц:

1. **`delivery_routes`**  
   `id`, `companyId`, `scheduledDate` (date), `shift` (optional), `status` (`draft` | `assigned` | `in_progress` | `completed` | `cancelled`), `driverUserId` (nullable до назначения), `warehouseLabel` или `warehousePropertyId`, `createdAt`, `startedAt`, `completedAt`.

2. **`delivery_route_stops`**  
   `id`, `routeId`, `sortOrder` (int; меняется водителем/менеджером), `kind` (`warehouse` | `property`), `propertyId` (nullable для склада), `status` (`pending` | `arrived` | `done`), timestamps.

3. **`delivery_stop_supply_lines`** (junction)  
   `stopId`, `supplyRequestItemId`, `quantity` (decimal, если нужно дробить строку между остановками — редко; иначе 1:1 на stop).

Связь со строками: при «включении в маршрут» обновлять `supply_request_items` ссылкой `deliveryRouteId` / `includedInStopId` или через junction только (предпочтительнее для аудита).

## 7. API (черновик)

- `POST /logistics/routes/from-pool` — собрать маршрут из выбранных id строк/пула.  
- `PATCH /logistics/routes/:id/assign-driver` — назначить водителя.  
- `PATCH /logistics/routes/:id/stops/reorder` — новый порядок остановок (менеджер или водитель по политике).  
- `POST /logistics/routes/:id/start` — водитель: начать смену/маршрут.  
- `POST /logistics/routes/stops/:stopId/arrive` | `complete` — с опциональным телом `{ photoUrls, lineConfirmations[] }`.

Точные пути согласовать с префиксом API (`/tasks` vs `/logistics`).

## 9. Резюме одной строкой (для Cursor / реализации)

Флоу передачи водителю должен опираться на сущности **Route** и **Stop**: после действия менеджера «отправить в доставку» утверждённые товары группируются по **`propertyId`** в единый **маршрутный лист** (склад → остановки на объектах). Водителю назначается **маршрут целиком**, а в UI — **линейный сценарий**: сбор на складе → последовательность остановок (с возможностью **гибкой перестановки** порядка водителем) → выгрузка на каждой точке с локальным чек-листом.
