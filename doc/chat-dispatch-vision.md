# Chat dispatch — vision и roadmap (v2/v3 и шире)

Документ задаёт **продуктовое видение**, нефункциональные темы и фазы **после и вокруг** минимальной реализации.

**Контракты v1 для кода (типы, JSON Schema, идемпотентность, сущности, emergency):** [`chat-dispatch-spec.md`](./chat-dispatch-spec.md) — при реализации агента опираться на него, чтобы не смешивать scope.

---

## Классификация гостевых запросов и авто-диспатч (обзор)

Документ ниже задаёт целевое поведение и нефункциональные требования для **production-продукта** уровня guest-ops / STR / PMS. Текущая реализация в коде может отличаться.

**Цель:** убрать разрыв «ИИ сказал „уточню у хозяина“, а операции не произошло» и выровнять RentAI на практики **2026+**: классификация + политики + надёжный пайплайн + безопасность + наблюдаемость.

---

## Проблема и ценность

- Гость пишет операционный запрос (полотенца, поломка, шум…).
- Ответ в чате без **создания работы в системе** = потерянная ценность.
- **Service Request Auto-Dispatch:** сообщение → классификация → при необходимости задача + уведомление исполнителю + **честный** ответ гостю в рамках **политики** (SLA, тексты, эскалации).

---

## Архитектура (целевая)

| Слой | Роль |
|------|------|
| **LLM** | Семантика: намерение, нормализованная суть запроса, язык; **structured output** (JSON) с валидацией схемой. |
| **Модуль политик (dispatch policy)** | Детерминированно: создавать ли задачу, тип, приоритет, исполнитель, эскалация, **разрешённые SLA-тексты** — с учётом property / portfolio / расписания / таймзоны. |
| **Задачи + уведомления** | Создание задачи с `source: chat`, `chatMessageId`; push / Telegram по правилам; **идемпотентность** на API. |
| **UI** | Бейдж «задача создана» у сообщения; в Kanban — источник из чата; у персонала — контекст «почему создана» (классификация + политика). |

**Принцип:** нельзя «одинаково для всех объектов» — настройки **property / portfolio / расписание**, а не только глобальный промпт.

---

## Таксономия намерений (черновик)

Имена intent — предмет согласования в коде; маппинг на политики — **всегда через модуль политик**.

| Intent | Типичное действие |
|--------|-------------------|
| `supply_request` | Задача → горничная / снабжение |
| `maintenance` | Задача → техник; при необходимости менеджер |
| `complaint` | Задача + эскалация по политике |
| `access` | Срочная эскалация (замок, не могу войти) |
| `information` | Ответ из KB / шаблонов, **без** задачи |

---

## Контекст проживания и бизнес-логика STR

Production-система не создаёт операционные задачи «в вакууме».

| Требование | Описание |
|------------|----------|
| **Бронь / stay** | Привязка к активному заезду (или явное правило для edge cases). Не создавать доставку полотенец без контекста гостя в номере, если это задано политикой. |
| **Юнит** | Один property — несколько юнитов: задача и исполнитель привязаны к **правильному unit**, если он известен из брони/чата. |
| **Таймзона объекта** | SLA «до вечера», ночные эскалации, «тихие часы» считаются в **локальном времени объекта**. |
| **Идемпотентность по смыслу** | Повтор «где полотенца?» за короткое окно — не плодить дубликаты; правила в политике + технический ключ идемпотентности. |

## Omnichannel

Одна и та же логика классификации и политик должна применяться ко **всем каналам**, которые подключаются к RentAI (веб-чат, Telegram, в перспективе WhatsApp / OTA messaging).

| Требование | Описание |
|------------|----------|
| **Единый пайплайн** | После нормализации входа в «текст + метаданные» — общий шаг classify → policy → task. |
| **Единый thread** | История и политики не расходятся между каналами для одного гостя/брони. |

---

## Безопасность и управляемость AI (production)

| Требование | Описание |
|------------|----------|
| **Prompt injection** | Гостевой текст не должен переопределять системные инструкции или извлекать внутренние данные. Отдельные guardrails в промпте и, при необходимости, фильтрация входа. |
| **Structured output** | JSON от модели валидируется **схемой** (JSON Schema); при невалидном ответе — retry с усечённым/исправляющим промптом или fallback в ручную очередь. |
| **Маршрутизация моделей** | По возможности: лёгкий вызов для классификации + основной для ответа — контроль **стоимости и латентности**; конфигурируемо per env / per rollout. |
| **PII** | Цитаты гостя в Telegram, задачах и логах — осознанно: минимизация, сроки хранения, согласие в рамках продукта (см. комплаенс). |

---

## Надёжность пайплайна

| Требование | Описание |
|------------|----------|
| **Идемпотентность API** | Заголовок или поле `Idempotency-Key` на создание задачи из сообщения — защита от повторов сети/клиента. |
| **Очередь и retry** | Если после ответа гостю создание задачи упало — не терять событие: повтор обработки или явная ошибка в мониторинге. |
| **Низкая уверенность** | Поле `confidence` (или аналог) из классификации: при пороге ниже настроенного — **не автосоздавать** задачу или создавать с флагом «требует проверки» + попадание в inbox менеджера. |
| **Dead-letter / ручная очередь** | Сообщения с ошибкой парсинга/политики — видимы менеджеру, с возможностью создать задачу вручную. |
| **Feature flags** | Включение авто-диспатча **per property** (или portfolio) для постепенного rollout. |

---

## Качество и регрессии (eval)

| Требование | Описание |
|------------|----------|
| **Набор сценариев** | Фиксированный набор сообщений (RU/EN и др.) с ожидаемым intent и действием — прогон при изменении промптов и моделей. |
| **Метрики** | В перспективе: precision/recall по intent, доля ручных исправлений, latency p95/p99 пайплайна чата. |
| **Версионирование промптов** | Желательно хранить версию системного промпта / политики в логе решения для отладки. |

## Продуктовое замыкание цикла

| Тема | Описание |
|------|----------|
| **Проактивность** | Pre-arrival / триггеры (Wi‑Fi, выезд, инструкции) снижают долю «информационного» шума в классификаторе — отдельная линия продукта, согласованная с чатом. |
| **После выполнения задачи** | Опционально по политике: авто-сообщение гостю («полотенца доставлены») — v2+. |
| **Обратная связь** | Короткий опрос «вопрос решён?» — для качества сервиса и будущего дообучения (v2+). |

---

## Персонал и поле

| Тема | Описание |
|------|----------|
| **Объяснимость для staff** | В задаче кратко: источник (чат), извлечённый запрос, применённая политика — чтобы исполнитель понимал контекст. |
| **Доказательство выполнения** | Фото / чеклист — по существующим модулям задач; не блокирует v1 классификации. |
| **Смены / доступность** | v2+: не назначать исполнителю вне смены, если это критично для клиента. |

## Комплаенс и аудит

| Тема | Описание |
|------|----------|
| **Данные гостя** | Цели обработки, сроки, экспорт/удаление по запросу — в рамках общей политики продукта. |
| **Аудит политик** | Кто изменил правила маршрутизации и когда — для B2B и споров (v2+). |

## Дополнительно: практики 2026+ (явно дополнить спецификацию)

Ниже — темы, которые легко упустить при фокусе на «классификация + задача», но которые отличают зрелый production от пилота.

### Критические и чувствительные сценарии

| Тема | Описание |
|------|----------|
| **Чрезвычайные ситуации** | Пожар, утечка газа, угроза жизни, острые медицинские случаи — **не** сводить к «создали задачу горничной». Нужны: отдельный класс/ключевые слова, **немедленная эскалация** (звонок/SMS/Telegram по контактам объекта), шаблон ответа гостю «вызовите 112 / экстренные службы». LLM — вспомогательный; правила и playbooks важнее. |
| **Безопасность и правопорядок** | Кража, насилие, домогательства — эскалация человеку + возможная политика **не хранить** полный текст в открытом виде в задаче (обезличивание в логах по настройке). |
| **«Хочу человека»** | Явный запрос живого менеджера / отказ от бота — приоритетный handoff: остановка автответов по политике, флаг разговора, уведомление дежурному. |

### Злоупотребления и устойчивость

| Тема | Описание |
|------|----------|
| **Rate limiting** | Лимиты сообщений с одного гостя/сессии/IP (и per property) — защита от спама, флуда и раздувания счёта за LLM. |
| **Злоупотребление задачами** | Пороги: слишком много авто-задач за период → уведомление менеджеру или пауза автодиспатча для сессии. |
| **Контент-модерация (опционально)** | Оскорбительный/неприемлемый контент — политика показа персоналу и хранения (юрисдикции различаются). |

### Стоимость и масштаб

| Тема | Описание |
|------|----------|
| **Бюджет на AI** | Лимиты токенов/стоимости на property или организацию в сутки; при превышении — деградация (короче ответ, только правила без второго вызова LLM). |
| **Кэширование** | Для повторяющихся информационных вопросов — опора на KB + детерминированные ответы, чтобы не гонять один и тот же запрос в LLM бесконечно. |

### Мультитенантность и изоляция

| Тема | Описание |
|------|----------|
| **Границы данных** | Управляющая компания A не должна видеть задачи/чаты B: изоляция на уровне tenant/org в запросах и политиках. |
| **Секреты и логи** | Не логировать полные промпты с персональными данными в production; ротация ключей API. |

### Международность и доступность

| Тема | Описание |
|------|----------|
| **Языки** | Классификация и ответ в языке гостя (или политика «всегда EN для staff»); eval на нескольких языках. |
| **Доступность UI** | Чат для гостя — базовые требования a11y (клавиатура, контраст) для B2B-контрактов и репутации. |

### Операционная связка

| Тема | Описание |
|------|----------|
| **Подрядчики** | Maintenance через внешнего подрядчика — создание задачи с типом «внешний», уведомление на email/SMS вендора по политике (v2+). |
| **Споры по факту** | Гость говорит «не решили», staff закрыл задачу — отдельный продуктовый поток (reopen, эскалация), не только классификатор. |
| **Human-in-the-loop для обучения** | Разметка ошибок классификации менеджером → будущий датасет для v3; без этого fine-tune бессмысленен. |

### Наблюдаемость и SRE (расширение)

| Тема | Описание |
|------|----------|
| **Трассировка** | Один `correlationId` на цепочку: сообщение → классификация → политика → задача → ответ — для поддержки и инцидентов. |
| **Алерты** | Рост ошибок JSON, рост latency, рост «ручной очереди» — пороги в мониторинге. |

### Второй слой: что часто забывают в первой спецификации

| Тема | Описание |
|------|----------|
| **Мультитурный контекст** | Сообщения вроде «то же самое», «ещё раз», «как вы писали» требуют учёта **истории диалога** при классификации; иначе intent ломается. |
| **Мультимодальность** | Фото поломки, скрин, голосовое — в 2026+ это норма: либо отдельный путь (описание из изображения → тот же пайплайн), либо явное «не поддерживается» в v1 с понятным UX. |
| **Circuit breaker провайдера LLM** | При недоступности API — деградация: шаблон «приняли запрос, менеджер ответит», **не** бесконечный спиннер; ретраи с backoff; не дублировать задачи при повторе. |
| **A/B тесты и канареечный rollout** | Сравнение промптов/моделей на доле трафика (per org/property) без поломки всего продукта. |
| **Свежесть базы знаний** | Устаревший KB даёт неверные «information»-ответы; нужны **сигналы устаревания**, периодический аудит, связь с авто-диспатчем (не подменять фактическую политику галлюцинацией). |
| **Праздники и пик сезона** | SLA и доступность персонала **не линейны** — отдельные правила в политиках (праздники, высокий сезон). |
| **Верификация гостя** | Перед выдачей **чувствительных** данных (коды доступа, Wi‑Fi с логированием) — политика: только после подтверждения брони / последних цифр телефона / deep link из OTA — защита от социальной инженерии. |
| **Интеграции наружу** | Outbox / webhooks: «задача создана из чата» → внешний PMS или биллинг для enterprise; идемпотентность на стороне получателя. |
| **Резидентность и DPIA** | Для EU/enterprise: регион хранения и обработки, список **субпроцессоров** (LLM-провайдер), DPIA под автоматизированные решения — прозрачность для B2B. |
| **Прозрачность «бот/ИИ»** | В ряде юрисдикций и контрактов — явное раскрытие, что отвечает ИИ и как подключить человека; снижает репутационный риск. |
| **Юридический аудит обещаний** | Что именно пообещал бот (лог текста ответа + связь с задачей) — для споров с гостем и страховыми кейсами. |
| **Миграция моделей** | План отката при смене модели; совместимость JSON-схемы; не «вчера GPT, завтра другая модель» без регрессии. |

## Риски (сводка)

- Ошибки классификации → отмена / коррекция задачи менеджером; низкая уверенность → ручная очередь.
- **SLA в тексте** только из политики или шаблонов, не «галлюцинация» срока.
- Наблюдаемость: логирование решения политики, `chatMessageId`, версии промпта при необходимости.
- **Экстренные и правовые сценарии** не должны полагаться только на «задачу в Kanban» — см. раздел «Критические и чувствительные сценарии».

## Фазы roadmap

Реализация **v1** в коде: типы, JSON Schema, миграции, идемпотентность, emergency — в [`chat-dispatch-spec.md`](./chat-dispatch-spec.md).

### v1 — production-ready MVP

- Structured classification + валидация JSON; интеграция в пайплайн после сохранения сообщения гостя.
- Модуль политик с **глобальными дефолтами** и **пер-property overrides** (вкл/выкл автозадач, assignee по роли, запрет произвольных SLA в тексте).
- Создание задачи с `source: chat`, связь с сообщением; **идемпотентность** и базовое правило против дубликатов.
- **Feature flag** per property; **retry** или явная деградация при сбое создания задачи.
- Минимальный **eval-набор** сценариев в CI или ручной чеклист на staging.
- Связь задача ↔ сообщение в API и в UI задач (метка источника).

### v2 — масштаб управляющих

- Portfolio, расписания (ночь / выходные), матрица категория → роль / человек; UI настроек политик.
- Метрики качества и latency; авто-сообщение гостю после закрытия задачи; опрос CSAT.
- Расширенный omnichannel при появлении каналов.

### v3 — зрелость

- Fine-tuned классификатор или дообучение на накопленных размеченных данных.
- Аудит версий правил; смены исполнителей; расширенный комплаенс.

## Engineering improvements backlog (позже)

- **Очередь обработки inbound WhatsApp (и при желании других вебхуков) через BullMQ / Redis:** сейчас Nest отвечает вебхуку `200 OK` и обрабатывает сообщение inline (`void …catch`). Для высокой нагрузки, длинных LLM-стримов и явных ретраев имеет смысл класть job в очередь и вынести загрузку медиа + LLM + исходящую отправку в воркер. Пока достаточно текущей схемы — пересмотреть при росте трафика или SLO.
