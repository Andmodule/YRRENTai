# Открыть / закрыть даты на Booking + автопродление календаря

## Зачем

Пока объект подключён к Booking через channel manager (XML, Zodomus), экстранет запрещает менять наличие и цены:
«Your inventory and prices can't be changed via extranet… use your channel manager», «Not allowed to edit hidden».
Инструмент Booking «Планирование наличия» тоже не открывает даты. Поэтому даты, которые никто не открыл,
так и остаются закрытыми.

Проверено 2026-10-12 на K22 Andersa (Booking 11021398, номер 1102139801, тариф Standard 39993723):
- `GET /availability` — с 2026-11-01 у тарифа `closed=1`, цена-заглушка 1180, при этом `availability=1`
  (наличие RentAI выгружает сам, ночью, на 366 дней — проблема не в нём);
- `POST /rates` с `closed:"0"` на одну ночь → Booking принял, `GET` показал `closed=0`;
  тот же запрос с `closed:"1"` вернул как было.

Раньше RentAI флаг `closed` не отправлял никогда («Цена на канале» и выгрузка наличия его не трогают),
а «Цена на канале» работает только по свободным открытым ночам — отсюда «No free OTA nights in range».

## Что сделано

**1. «Открыть / закрыть даты на Booking»** — календарь → свободная ячейка → «Открыть / закрыть даты на Booking»,
или выделить даты одного объекта → «Открыть / закрыть». То же, что «Планирование наличия» в Booking:

- объект, «Открыть продажи» / «Закрыть продажи», даты (3 дня / 30 / 60 / 3 месяца / год / свои, до 366 ночей),
  дни недели;
- цена при открытии: «Как сейчас на Booking» (закрытые откроются по своей цене, например 1180) / «Одна цена» /
  «Будни и выходные» (выходные — ночи пт и сб). С ценой по умолчанию меняются только закрытые ночи; галочка
  «Менять цену и у уже открытых дат» переоценивает и открытые;
- закрытие оставляет цену, которая стоит на Booking;
- сначала «Показать, что изменится» — RentAI читает Booking и показывает: сколько ночей откроется / закроется /
  сменит цену, что пропущено и почему, тариф, число запросов и примерное время. Отправка — только после этого;
- отправка идёт в фоне (окно можно закрыть), в конце RentAI перечитывает даты с Booking и пишет, всё ли совпало.

Никогда не трогает: ночи, проданные на Booking (`booked>0`), и ночи с бронью или блоком в RentAI.
Не отправит цену ниже «Цены → Минимальные цены». Прошедшие даты не меняет.

**2. «Автопродление»** — блок внизу того же окна, по объекту: «Держать продажи открытыми вперёд» на 1/2/3/6 месяцев
или год, цена новых дат (и, если нужно, цена выходных). Раз в сутки (по умолчанию 04:00 UTC, после ночной выгрузки
наличия в 03:00) открывает дни, которые вошли в окно «сегодня + N дней», по этой цене — как продление наличия
в Booking. Высокая цена на дальних датах — метод администратора (защита от дешёвых броней на концерты и форс-мажор).

- Начинает с края окна на момент включения: даты ближе края — дело кнопки «Открыть даты».
- Открытые даты не трогает (цена остаётся), открывает только закрытые.
- Даты, закрытые вручную кнопкой «Закрыть продажи» за краем, запоминает и не открывает; открыли вручную — забывает.
- При ошибке край не двигается — на следующую ночь повторит.

## Как включить

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `ZODOMUS_CALENDAR_DATES_ENABLED` | `false` | Кнопка «Открыть / закрыть даты». Выключено — API 503, кнопок нет. |
| `ZODOMUS_CALENDAR_AUTO_OPEN_ENABLED` | `false` | Автопродление (нужен и первый флаг + миграция). |
| `ZODOMUS_CALENDAR_AUTO_OPEN_DRY_RUN` | `true` | Автопродление только пишет, что открыло бы. |
| `ZODOMUS_CALENDAR_AUTO_OPEN_HOUR_UTC` | `4` | Час ежедневного запуска. |

Порядок: выложить код (с выключенными флагами ничего не меняется) → `ZODOMUS_CALENDAR_DATES_ENABLED=true` →
пробно открыть 1–3 ночи на K22 и сверить в экстранете → дальше пользоваться. Автопродление: миграция →
`ZODOMUS_CALENDAR_AUTO_OPEN_ENABLED=true` (остаётся тестовый режим) → включить на объекте, посмотреть «Последний
запуск» утром → `ZODOMUS_CALENDAR_AUTO_OPEN_DRY_RUN=false`.

### Миграция (только для автопродления)

`1778500000000-calendar-auto-open-settings` — одна новая таблица, существующие не трогает. На Render нет Shell,
поэтому — SQL в консоли Neon (проект RENTAI, ветка production, база neondb):

```sql
CREATE TABLE IF NOT EXISTS "calendar_auto_open_settings" (
  "propertyId" uuid NOT NULL,
  "enabled" boolean NOT NULL DEFAULT false,
  "horizonDays" smallint NOT NULL,
  "priceMinor" integer NOT NULL,
  "weekendPriceMinor" integer,
  "openedUntil" character varying(10),
  "keepClosed" jsonb NOT NULL DEFAULT '[]'::jsonb,
  "lastRunAt" TIMESTAMP WITH TIME ZONE,
  "lastResult" jsonb,
  "updatedAt" TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT now(),
  CONSTRAINT "PK_calendar_auto_open_settings" PRIMARY KEY ("propertyId"),
  CONSTRAINT "FK_calendar_auto_open_settings_property" FOREIGN KEY ("propertyId") REFERENCES "properties"("id") ON DELETE CASCADE
);
INSERT INTO "migrations" ("timestamp", "name") VALUES (1778500000000, 'CalendarAutoOpenSettings1778500000000');
```

Откат таблицы: `DROP TABLE IF EXISTS "calendar_auto_open_settings";` и удалить строку из `"migrations"`.

## Нагрузка на Zodomus

Все запросы идут через общий ограничитель клиента (`ZODOMUS_MAX_REQUESTS_PER_MINUTE`, по умолчанию 20 в минуту,
по одному). `GET /availability` — окнами по 28 ночей (Zodomus не даёт больше месяца). `POST /rates` — по одному
на отрезок подряд идущих ночей с одной ценой и одним состоянием, не длиннее 28 ночей. Примеры: 3 месяца одной
ценой — 4 записи + 4 чтения + 4 проверочных чтения; 3 месяца «будни/выходные» — около 26 записей (≈2 мин).
Больше 200 записей за раз не отправит (попросит диапазон короче или одну цену). После трёх ошибок подряд
останавливается. Прочитанное для предпросмотра переиспользуется 2 минуты, проверка после отправки читает заново.

## API

`/api/v1/calendar-dates` (OWNER, MANAGER, SUPERADMIN; при выключенном флаге — 503, кроме `status`):
`GET /status` · `POST /preview` · `POST /apply` (запускает в фоне) · `GET /job?propertyId=` (отчёт последнего
запуска, хранится в памяти — после перезапуска сервера пропадает) · `GET /auto?propertyId=` · `PUT /auto`.

Код: `backend/src/calendar-dates/*` (модуль подключён в `app.module.ts`, больше от него ничего не зависит),
`ZodomusService.setRates` получил необязательный `closed` (без него тело запроса прежнее — «Цена на канале» не
изменилась). Фронт: `frontend-user/src/modules/calendar/components/CalendarDatesSheet.tsx`,
`calendar-dates-api.ts`, `lib/calendar-dates.ts`. Тесты: `calendar-dates.*.spec.ts`, `calendar-auto-open.service.spec.ts`,
`zodomus.service.set-rates.spec.ts`, фронт — `lib/calendar-dates.spec.ts`.

## Откат

Флаги в `false` — кнопки исчезают, ночной запуск не идёт. Даты, уже открытые или закрытые на Booking, остаются
как есть — вернуть их можно этой же кнопкой (пока флаг включён) или запросом `POST /rates` на странице «Zodomus API».

## Не проверено на боевом Booking

- Отрезки длиннее одной ночи с `closed` (проба была на одной ночи) и цены «будни/выходные» на Booking.
- Принимает ли Booking открытие дат, которые экстранет называет «hidden», дальше чем на год вперёд.
- Тарифы, производные от Standard (например, невозвратный): открываются ли вместе с ним. У K22 `GET /availability`
  показывает только Standard — похоже, производные Booking считает сам.
